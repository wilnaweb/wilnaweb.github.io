# Astro Standards

This document defines how Astro must be used throughout the WIL.DEV project.

These rules are specific to Astro and complement the project's engineering standards.

Framework-specific features should always be implemented following these guidelines.

---

# Purpose

Astro is the foundation of the WIL.DEV project.

The objective is to maximize:

- Performance
- Simplicity
- Maintainability
- SEO
- Accessibility

Astro should be used according to its strengths.

---

# Architecture

The project follows a Static Site Generation (SSG) architecture.

Rendering occurs at build time.

There is no application server.

There is no backend.

Every page should be generated as static HTML whenever possible.

---

# Rendering Strategy

Prefer:

Static Rendering

↓

Server Rendering (Build Time)

↓

Client Rendering

Client-side rendering should always be the last option.

---

# Islands Architecture

Astro Islands should be used only when interactivity is required.

Examples:

- Theme Switcher
- Language Switcher
- Search
- Interactive widgets

Static content should never be hydrated.

---

# Client Directives

Choose the lightest directive that satisfies the requirement.

Preferred order:

client:visible

↓

client:idle

↓

client:load

Avoid:

client:only

unless absolutely necessary.

Hydrate only what must become interactive.

---

# Pages

Pages should remain lightweight.

Their responsibilities are limited to:

- Loading content
- Selecting layouts
- Rendering components

Pages must not contain business logic.

---

# Layouts

Layouts define page structure.

Examples:

- BaseLayout
- DefaultLayout
- ArticleLayout
- CaseStudyLayout

Layouts should not contain page-specific content.

---

# Components

Pages should be composed of reusable components.

Avoid large page-specific implementations.

If a pattern appears more than once, create a reusable component.

---

# Content Collections

Content must be loaded through Astro Content Collections.

Never read Markdown files directly.

Collections provide:

- Validation
- Type Safety
- Predictability

Use them consistently.

---

# Dynamic Routes

Dynamic routes should be generated during build.

Prefer:

getStaticPaths()

Avoid runtime routing.

---

# Data Loading

Data should be loaded as close as possible to the page.

Avoid loading unnecessary information.

Only retrieve the content required for rendering.

---

# Markdown Rendering

Markdown should remain the source of truth.

Components render content.

Components never own content.

---

# Routing

Use Astro's file-based routing.

Keep URLs:

- Stable
- Predictable
- Human-readable

Avoid unnecessary nesting.

---

# Imports

Prefer project aliases.

Good

```typescript
import Hero from "@/components/Hero";
```

Avoid

```typescript
import Hero from "../../../components/Hero";
```

---

# JavaScript

Avoid client-side JavaScript whenever Astro provides a static alternative.

Static HTML is always preferred.

---

# Scripts

Keep scripts isolated.

Avoid inline JavaScript inside pages.

Shared behavior should become reusable modules.

---

# Slots

Use slots to increase layout flexibility.

Avoid creating dozens of optional props for layout customization.

Composition is preferred.

---

# Metadata

Every page must expose metadata through the layout.

Metadata should include:

- Title
- Description
- Canonical URL
- Open Graph
- Twitter Card

Pages should never duplicate metadata logic.

---

# Assets

Images

Fonts

Icons

Static files

should use Astro's recommended optimization strategy whenever applicable.

Avoid unnecessary asset duplication.

---

# Error Pages

Provide dedicated pages for:

- 404
- 500 (if applicable)

Error pages should remain consistent with the rest of the website.

---

# Environment Variables

Environment variables should be accessed only when necessary.

Never expose sensitive values to the client.

---

# Build

The production build must:

- Compile successfully
- Produce static output
- Generate optimized HTML
- Generate optimized assets
- Produce no warnings

Warnings should be treated as technical debt.

---

# Astro Configuration

Centralize framework configuration.

Avoid scattered configuration across the project.

Configuration changes should be documented.

---

# Performance

Every Astro implementation should prioritize:

- Minimal HTML
- Minimal JavaScript
- Minimal CSS
- Static rendering
- Fast navigation

Performance is a core requirement.

---

# Accessibility

Every page generated by Astro must:

- Use semantic HTML
- Preserve heading hierarchy
- Support keyboard navigation
- Provide meaningful landmarks

Accessibility is mandatory.

---

# Anti-Patterns

Avoid:

- Hydrating entire pages
- Loading unnecessary JavaScript
- Business logic inside pages
- Reading Markdown manually
- Duplicating layouts
- Deep routing hierarchies
- Page-specific components that should be reusable

---

# Review Checklist

Before approving an Astro implementation, verify:

✓ Static rendering is used whenever possible.

✓ Hydration is justified.

✓ Content comes from Collections.

✓ Layout responsibilities are respected.

✓ Components are reusable.

✓ Routing follows conventions.

✓ Metadata is complete.

✓ Imports use project aliases.

✓ No unnecessary JavaScript exists.

---

# Definition of Good Astro Code

Good Astro code is:

- Static by default
- Lightweight
- Composable
- Predictable
- Easy to maintain
- Easy to expand

The framework should remain almost invisible.

Visitors should notice the website, not the technology behind it.

---

# Final Principle

Astro was chosen because it produces fast, simple and maintainable websites.

Every implementation should reinforce those strengths.

Whenever multiple Astro solutions exist, choose the one that:

- Generates less JavaScript
- Produces cleaner HTML
- Requires less complexity
- Preserves the project's architecture

Static-first is always the preferred approach.
