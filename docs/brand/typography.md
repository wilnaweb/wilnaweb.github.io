# Typography

Version: 2.0

---

# Purpose

This document defines the typography system for the WIL.DEV brand.

Typography is the primary visual element of the platform.

Unlike marketing websites that rely on visual effects, WIL.DEV communicates primarily through knowledge, engineering and documentation.

Typography is not decoration.

Typography is the interface.

---

# Typography Philosophy

The typography system should communicate:

- Engineering
- Confidence
- Precision
- Clarity
- Professionalism
- Calm

Reading should feel effortless.

Every typographic decision should improve understanding.

---

# Design Principles

Typography should never feel:

- decorative
- playful
- futuristic
- trendy
- aggressive
- compressed

Instead, it should feel:

- technical
- elegant
- modern
- timeless
- readable
- engineered

---

# Typography Goals

The typography system should:

- improve readability
- reinforce hierarchy
- reduce cognitive load
- support long-form reading
- communicate confidence

The objective is not visual impact.

The objective is comprehension.

---

# Typography Hierarchy

The hierarchy should remain consistent throughout the platform.

```
Display

↓

H1

↓

H2

↓

H3

↓

H4

↓

Lead

↓

Body

↓

Small

↓

Caption

↓

Code
```

Every level should be immediately recognizable.

---

# Type Scale

The Design System should expose semantic typography tokens.

Examples:

```
--font-display

--font-h1

--font-h2

--font-h3

--font-h4

--font-lead

--font-body

--font-small

--font-caption

--font-code
```

Component implementations should consume semantic tokens rather than fixed font sizes.

---

# Font Families

The typography system uses only two font families.

Primary Sans Serif

↓

Monospace

Nothing else.

Consistency has priority over variety.

---

# Primary Typeface

The primary typeface is responsible for:

- interface
- navigation
- articles
- documentation
- headings
- forms
- buttons

Preferred characteristics:

- Neo-Grotesque
- Variable Font
- High readability
- Excellent Unicode support
- Multiple weights
- Long-term maintenance

Preferred candidates:

- Geist
- Inter
- IBM Plex Sans
- Manrope

Final selection will be validated during implementation.

---

# Monospace Typeface

The monospace family is reserved for:

- source code
- commands
- terminal output
- configuration
- technical snippets

Preferred characteristics:

- clear punctuation
- distinguishable symbols
- balanced spacing
- programming readability

Preferred candidates:

- Geist Mono
- JetBrains Mono
- IBM Plex Mono

---

# Typography Pairing

The relationship should be:

Sans Serif

↓

Monospace

Nothing more.

Introducing additional font families should require strong justification.

---

# Font Weights

Recommended usage:

Regular

Medium

SemiBold

Bold

Avoid:

Thin

ExtraLight

Black

Typography should communicate confidence through balance rather than weight extremes.

---

# Line Length

Long-form reading should remain comfortable.

Recommended reading width:

60–75 characters per line.

Documentation pages may extend slightly when appropriate.

Very wide paragraphs should be avoided.

---

# Line Height

Body text should prioritize reading comfort.

Recommended principles:

- generous spacing
- relaxed rhythm
- consistent vertical flow

Whitespace is part of typography.

---

# Letter Spacing

Default tracking should be preserved whenever possible.

Minor adjustments are acceptable for:

- large headings
- all-caps labels
- navigation

Avoid excessive tracking.

---

# Vertical Rhythm

Typography establishes the rhythm of the interface.

The relationship between headings, paragraphs, lists and code blocks should remain consistent across the entire website.

A predictable rhythm improves comprehension.

---

# Paragraphs

Paragraphs should remain concise.

Avoid extremely long text blocks.

Reading should feel conversational without becoming informal.

---

# Lists

Lists should improve scanning.

Maintain generous spacing between list items.

Lists should never appear visually compressed.

---

# Blockquotes

Blockquotes communicate reflection.

They should appear elegant and understated.

The quotation should remain more important than its decoration.

---

# Tables

Tables should prioritize:

- readability
- alignment
- scanning

Typography inside tables should remain visually consistent with body text.

---

# Code Blocks

Code is part of the reading experience.

Code blocks should communicate:

- precision
- structure
- clarity

Avoid excessive syntax highlighting.

The code should remain the protagonist.

---

# Numbers

Prefer tabular numbers for:

- metrics
- statistics
- financial values
- technical tables
- timelines

Alignment improves readability.

---

# Links

Links should be recognizable without becoming visually dominant.

Interaction should rely on:

- color
- underline
- hover feedback

Never on color alone.

---

# Accessibility

Typography must satisfy:

- WCAG AA contrast
- scalable sizing
- zoom compatibility
- readable line spacing
- responsive behavior

Accessibility is part of engineering quality.

---

# Responsive Typography

Typography should scale naturally.

Avoid dramatic jumps between breakpoints.

Reading comfort should remain consistent across all devices.

---

# Font Loading

Fonts should be:

- self-hosted
- optimized
- variable
- preloaded when critical

Performance is part of typography.

---

# Typography Anti-Patterns

Avoid:

- decorative fonts
- script fonts
- condensed fonts
- multiple font families
- inconsistent hierarchy
- oversized headings
- tiny body text

The typography should remain timeless.

---

# Typography Personality

The typography should make visitors think:

"This engineer writes clearly."

Not:

"This website uses beautiful fonts."

Typography succeeds when it becomes invisible.

---

# Success Criteria

The typography system is successful if it communicates:

- confidence
- clarity
- engineering
- professionalism
- calm

without drawing attention to itself.

---

# Final Principle

Typography is the voice of the WIL.DEV brand.

It should quietly reinforce every engineering decision made throughout the platform.

Every heading.

Every paragraph.

Every code block.

Every article.

Should support one simple idea:

> Engineering Complex Solutions.
